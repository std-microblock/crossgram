# history-backfill

空闲时慢慢回读各会话的历史，把本地投影库里缺的部分补回来。

- **群聊**（平台声明 `capabilities.sequenceHistory: 'group'`，即 QQ）：用库里已有的 msgSeq 推导覆盖区间，按下面的顺序补：
  1. 顶部空洞，也就是停机期间缺的、最新消息之前的那一段；
  2. 区间之间的空洞；
  3. 向更早方向追溯，直到会话起点或 `maxAgeDays`。

  请求走 `beforeSequence`。上游返回的原始区间（`coverage`）包含被撤回、被过滤的序号，这些序号不会被反复请求。
- **私聊或不支持序号的平台**：以库里最早的一条为锚点向前翻页，直到上游没有更多为止。
- 回填只写本地库，不发 update，也不改未读数和提及。
- 只在账号最近 `idleAfterMs` 内没有客户端操作时工作。`updates.*`、`help.*`、`account.updateStatus` 这类后台 RPC 不算操作。每次最多发一个上游请求，两次请求之间至少间隔 `intervalMs`，另加随机抖动。每个账号每天最多发 `dailyRequestCap` 次请求。
- 进度只保存在内存里，重启后从库里已存的 msgSeq 重新推导。被撤回的序号会在下一次按序号请求时重新确认覆盖。

## WebUI

在 Observe → History backfill 页面可以看到：

- 每个账号的状态：在等空闲、工作中、到达当日上限、已完成；
- 每个会话的覆盖范围、空洞数量和缺失的序号数、最早消息的时间、失败重试信息；
- 最近的请求记录。

页面右上角可以暂停或开始回填。这个开关只在运行时生效，不会写回配置。失败或已到底的会话可以点「Retry」重新检查。

## 配置

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 启动时是否开启 |
| `idleAfterMs` | `60000` | 账号多久没有客户端操作才算空闲 |
| `intervalMs` | `3000` | 两次上游请求的最小间隔 |
| `pageSize` | `50` | 每次请求的消息条数 |
| `dailyRequestCap` | `3000` | 每个账号每天（UTC）的请求上限 |
| `maxAgeDays` | `180` | 向前追溯的最大天数，`0` 表示不限 |

依赖 bridge 提供的 `historySync` 服务和 `webui`。按序号回填要求 qqnt-bridge 协议版本不低于 36；版本更旧时，序号请求会直接报错并进入退避，不会把最新一页误当作回填结果。
