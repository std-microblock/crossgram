# MTProto Relay —— 架构设计与开发计划

> cordis-native 实现，仓库：`mtproto-relay-cordis`。
> 目标：做一个"镜像 Telegram 服务器"，让打过补丁的官方客户端（Telegram Desktop / TDLib）或 mtcute 连进来，把每个账户按需路由到 **官方 Telegram（relay）** 或 **各 IM 平台（bridge）**。
> 一切皆 cordis 插件；数据库用 **minato**（`@cordisjs/plugin-database`），不用 TypeORM。

## 2. 架构

### 2.1 分层

```
Client (打补丁的 tdesktop / mtcute)
   │  TCP + obfuscated/abridged framing
   ▼
┌───────────────────────────────────────────────┐
│ ctx.mtproto  (@mtproto-relay/mtproto)          │  原生 cordis Service
│  · 直接持有 net.Server + 每连接一个 ServerSession │  (@cordisjs/plugin-server 模式)
│  · 协议：握手 / 加解密 / PFS / 容器 / ack / salt  │
│  · auth key 持久化 + 多密钥路由                  │
│  · register(method,h) / fallback(h) —— ctx.effect │  ← HMR 友好
└──────────────────┬────────────────────────────┘
                   │ 解密后的 tl.RpcMethod
                   ▼
┌───────────────────────────────────────────────┐
│ 路由层（按账户）—— 见 §3                          │
│   authKeyId → routeId → 对应后端的 handler 集      │
└──────┬───────────────────────────┬─────────────┘
       ▼                           ▼
┌──────────────┐          ┌────────────────────────┐
│ Relay 后端    │          │ Bridge 后端             │
│ 透传官方 TG   │          │ IM 平台适配（合成 TL）    │
│ (#16)        │          │  · ctx.database (minato) │
└──────────────┘          │  · ctx.server (HTTP 登录) │
                          │  · IMPlatform 抽象        │
                          └────────────────────────┘
```

### 2.2 各包职责

- **`@mtproto-relay/mtproto`** —— MTProto 协议 + 服务器 Service。对外只暴露 `ctx.mtproto`（register/fallback/broadcastUpdate/rsaKey）。协议内部件（ServerSession/ServerConnection/ServerAuthKey/握手/rsa-keygen/message-id/dispatcher）都是实现细节。
- **`@mtproto-relay/bridge`** —— IM 平台桥接插件。定义 minato 模型、HTTP 虚拟号登录、把 RPC 合成为 IM 平台操作。含 `IMPlatform` 抽象 + `StaticDemoPlatform`。
- **`@mtproto-relay/relay`**（待建）—— 透传插件：上游 `BaseTelegramClient`，`fallback` 直接转发。

### 2.3 cordis 关键机制（为什么这么设计）
- **一切皆插件 + 依赖注入**：后端 `inject: ['mtproto','database','model','server']`，cordis 自动排序启动（db 先于 bridge），依赖消失自动卸载。
- **effect = 自动清理**：handler 用 `ctx.mtproto.register()`（内部 `ctx.effect`）注册，绑定到调用方 fiber —— 热重载/卸载时 handler 自动增删，**服务器和在线连接不掉**。
- **HMR**：boilerplate 用 `@cordiverse/tsx` + `@cordisjs/plugin-hmr` 监听 `packages/`，改 handler 即时生效。

## 3. 多账户路由设计（重点）

**需求**：一个客户端多账户，各账户路由到不同后端。例：
`账户 A → 官方 Telegram relay`、`B → relay 平台 A`、`C → relay 平台 B`。

**设计**：
1. `Mtproto` Service 内维护 **RouteRegistry**：`routeId → RpcDispatcher`。每个后端插件启动时注册一条 route（`relay:official`、`bridge:platformA`…），用 `ctx.isolate` 给各后端独立实例/配置。
2. **绑定** `authKeyId → { routeId, platformSession }`，在 `auth.signIn` 成功时确定并用 minato 持久化：
   - 虚拟号前缀决定平台（`+99901…`→平台A、`+99902…`→平台B）；
   - 真实 TG 登录 → `relay:official`。
3. **派发**：`ServerSession` 登录前用「默认 route」（help/auth 这些无账户上下文的）；登录后按本连接绑定的 `routeId` 派发到对应后端的 dispatcher。
4. **需要改 mtproto-core**：目前是全局单一 dispatcher；要改成 session 持有 `routeId`、按账户选 dispatcher。`ServerRpcContext` 增加 `routeId`。

**要点**：mtproto 传输/会话层与账户无关（共享）；「按账户路由」只发生在 RPC 派发这一层。

## 5. 路线图

### ✅ 已完成
- **Phase 0** 传输 + DH 握手 + PFS + auth key 持久化（协议核心，11 测试）。
- **Phase 1a** 原生 `Mtproto` Service + `cordis run` 启动 + HMR。
- **Phase 1b** Bridge 登录链路（minato 模型 + HTTP 虚拟号 + auth.sendCode/signIn + 够进主界面的初始同步）。

### ⬜ #17 Bridge 补全：真实会话与消息（下一步优先）
- **裸 `Vector` 返回支持**：给 `_sendRpcResult` 加 `Vector<X>` 序列化（`0x1cb5c415`+count+items）。`users.getUsers`、旧版 `messages.getDialogFilters` 等返回裸 vector，现在只支持带 `_` 的对象和 Bool。
- **真实 `messages.getDialogs`/`getHistory`/`getMessages`**：把 `IMPlatform` 数据构造成合法 TL（Dialog/Message/Peer/User + 正确 flags），会话列表真正显示。
- `messages.sendMessage` → `platform.sendMessage` + 构造 `updates`。
- `users.getUsers`/`getFullUser`、`contacts.getContacts`。
- **UpdateManager**：`pts/qts/seq` 计数 + `IMEvent → MTPUpdates` + `ctx.mtproto.broadcastUpdate` 主动推送（push-only 平台的核心）。
- 完善登录 e2e：登录 → getDialogs → sendMessage → 收到 push update。

### ⬜ #16 Relay 模式 + 多账户路由
- **Relay 插件**：`inject ['mtproto']`，上游 `BaseTelegramClient`（`ctx.effect` 管理连接），`ctx.mtproto.fallback` 透传所有 RPC，转发上游 updates。可选 transport logger 记录明文。
- **多账户路由**（§3）：RouteRegistry + `ServerSession` 按 `routeId` 派发 + `authKeyId→route` 持久化 + 登录时按虚拟号/真实登录解析。

### ⬜ 后续
- **文件传输**：`upload.getFile`/`saveFilePart`（单 DC，file_reference 不过期）；`platform.downloadMedia/sendMedia`。
- **WebUI**：用 boilerplate 自带的 webui 管理 session / 平台 / 路由。
- **测试工具复用**：把 mtproto e2e 的握手 client helper 抽成共享 test-util（现在 bridge e2e 复制了一份）。
- **平台特异功能**：自定义 emoji / 角色 / 富文本（PlatformFeatureSet）。

### 实现策略：一个 RPC 该由谁答？
- **Relay 账户**：`fallback` 全部透传给上游，几乎不用逐个实现。
- **Bridge 账户**：`help.*`/`auth.*`/`updates.*` 合成；`messages.*`/`users.*` 走平台适配；不支持的按能力声明返回空或错误。
- 「缺一个补一个」不可持续 —— Bridge 要按官端启动会调的一批（config/dialogFilters/getState/getDialogs/getUsers/contacts…）成体系地实现。

## 6. 已知坑（记录以免重犯）
- **手机号 `+` 前缀不一致**：客户端 `auth.sendCode` 发 `+999…`，`auth.signIn` 发 `999…`（无 `+`）！服务端必须统一 `replace(/\D/g,'')` 归一化再查/存库，否则 signIn 查不到 → `PHONE_NUMBER_UNOCCUPIED` → 登录卡死。（官端"输对码卡住"真因）
- **官端登录后先拉 `messages.getDialogFilters`**：不实现它会卡在加载界面进不去。
- **Telegram RSA 指纹**必须 `hex(reverse(sha1(TL(n)+TL(e))[-8]))`（补零 16 位），不能用 int64 `.toString(16)`（丢前导零）。
- **`boolTrue`/`boolFalse` 不在 mtcute writer map**：`_sendRpcResult` 已特判、按构造子 id 手写。
- **裸 `Vector` 返回**（`users.getUsers` 等）目前不支持序列化 —— 见 #17。
- **可选 string 字段传 `undefined` 不传 `null`**（mtcute writer 把 null 当"存在"写 string 会崩）。
- **`ctx.model` 与 `ctx.database` 是两个注入名**，都要 `inject`。
- **`future_salts` 构造子 id = 0xAE500895**（曾误写成 0xAE5008F7，严格客户端如 mtcute 会重连打断）。
