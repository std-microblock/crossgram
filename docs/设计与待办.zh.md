# CrossGram MTProto 服务 —— 架构设计与开发计划

> cordis-native 实现，仓库：`mtproto-relay-cordis`。
> 目标：提供一个面向打补丁 Telegram 客户端的 MTProto 服务，把 Telegram RPC 合成为各 IM 平台操作。
> 一切皆 Cordis 插件；数据库使用 minato（`@cordisjs/plugin-database`）。

---

## 1. 当前状态（2026-07-27）

| 能力 | 状态 |
|---|---|
| 混淆 + abridged 传输、DH 握手、PFS 临时密钥、auth.bindTempAuthKey | ✅ |
| auth key 持久化（`FileAuthKeyStore`，跨重启复用） | ✅ |
| 虚拟号登录（WebUI 发号 → auth.sendCode/signIn） | ✅ |
| 登录后初始同步（getConfig/getDialogFilters/updates.getState/…） | ✅ |
| 好友、会话、历史、发送和消息事件 | ✅ |
| 文件与媒体传输 | ✅ |
| QQNT、Discord、Matrix、Satori 与 static 参考平台 | ✅ / 按适配器能力 |

官方 Telegram 透传后端已经删除。MTProto 服务现在通过 Cordis RPC 事件管线完成路由，
bridge 是唯一账户后端，不再维护后端 route、route resolver 或 auth-key route binding。

## 2. 架构

```
Client（打补丁的 Telegram Desktop / TDLib）
   │ TCP + obfuscated/abridged framing
   ▼
┌───────────────────────────────────────────────┐
│ ctx.mtproto  (@mtproto-relay/mtproto)          │
│ · net.Server + 每连接一个 ServerSession         │
│ · 握手、加解密、PFS、容器、ack、salt            │
│ · auth key 持久化与同 key 多连接共享状态         │
│ · register(method, handler)                    │
└──────────────────┬────────────────────────────┘
                   │ 解密后的 tl.RpcMethod
                   ▼
┌───────────────────────────────────────────────┐
│ Bridge (@mtproto-relay/bridge)                 │
│ · 虚拟手机号登录与 auth-key/platform 绑定       │
│ · 合成 Telegram TL 对象和 updates              │
│ · 消息、媒体、贴纸、reaction 与历史存储         │
└──────────────────┬────────────────────────────┘
                   │ IMPlatform
                   ▼
       QQNT / Discord / Matrix / Satori / static
```

### 包职责

- **`@mtproto-relay/mtproto`**：MTProto 协议与服务器 Service。对外暴露
  `ctx.mtproto.register()`、定向/广播 update、监听端口和 RSA key。
- **`@mtproto-relay/bridge`**：定义数据库模型、平台账户 WebUI、虚拟号登录和 RPC 到
  `IMPlatform` 的映射。
- **`@mtproto-relay/platform-*`**：平台适配器，只负责平台 API 与事件。
- **`@mtproto-relay/telegram-resources`**：Telegram reaction、emoji、sticker 等渲染资源。
- **`@mtproto-relay/test-suite`**：跨包契约测试和真实 socket e2e。

handler 通过 `ctx.mtproto.register()` 注册，内部使用 `ctx.effect` 管理生命周期；
插件热重载或卸载时 handler 自动清理，服务器和现有连接无需重启。

## 3. 单逻辑 DC、多地址模型

bridge 的 `help.getConfig` 只公布一个逻辑数据中心：主 `dcOption` 的 ID、主机和端口来自
`dcId`、`serverHost` 和 `serverPort`；`altEndpoints` 中的 `host:port` 或 `[IPv6]:port`
地址会按配置顺序紧随主地址，并使用相同的 `dcId` 和 `dcOption` 标志。因此客户端不会根据
配置创建其它逻辑 DC 或执行跨 DC 的 `auth.exportAuthorization/auth.importAuthorization`。

```yaml
- id: bridge01
  name: '@mtproto-relay/bridge'
  config:
    dcId: 1
    serverHost: 192.168.1.10
    serverPort: 4430
    altEndpoints:
      - 192.168.1.11:4430
      - bridge-backup.example:8443
      - '[2001:db8::1]:4430'
```

bridge 只向客户端公告主地址和备用地址，不做端点健康检查，也不会主动 fallback；客户端可在
主地址不可用时自行决定是否尝试已公告的备用地址。备用地址必须使用 `host:port` 或
`[IPv6]:port` 格式，裸 IPv6 会被配置校验拒绝。首次 bootstrap 仍使用二进制补丁写入的主
地址。桌面端补丁仍会替换客户端内置的所有官方 DC 地址和 RSA 公钥，这是启动前的安全措施：
客户端最初可能从任一内置 DC 入口发起连接，所有入口都必须落到 CrossGram；连接成功后，
服务端再公布同一逻辑 DC 的主地址和备用地址。

## 4. 数据模型

核心账户表：

- `mtproto_auth_session`：虚拟手机号、TOTP secret 与平台会话。
- `mtproto_platform_session`：平台用户、凭据、元数据和启用状态。
- `mtproto_auth_binding`：永久 auth key 到平台会话的绑定；同一 auth key 的并行连接共享状态。

消息和投影表：

- `mtproto_im_conversation`、`mtproto_im_user`、`mtproto_im_message`
- `mtproto_im_message_alias`、`mtproto_im_media`、`mtproto_tl_message_part`
- `mtproto_update_state`、`mtproto_channel_update_state`、`mtproto_update_delivery`
- sticker、reaction、ID counter 与 message ID epoch 相关表

不再存在 `mtproto_route_binding`；auth key 的持久化身份只由
`mtproto_auth_binding` 表达。

## 5. 实现原则

- MTProto 传输层只负责协议、会话与 RPC 派发，不感知平台类型。
- bridge 负责 Telegram 语义和持久化，平台适配器不构造 MTProto TL 对象。
- 同一永久 auth key 可以有多个主连接、上传连接或下载连接；进程内 bridge 状态按 auth key 共享。
- 不支持的 Telegram RPC 返回明确的 `METHOD_NOT_IMPLEMENTED` 或 bridge 定义的合法空结果。
- 客户端可见的媒体 `dcId` 与 bridge 配置保持一致。

---

## 6. 已知坑

- 客户端在 `auth.sendCode` 和 `auth.signIn` 中可能分别发送带/不带 `+` 的手机号，
  服务端必须先做数字归一化。
- `messages.getDialogFilters` 等启动 RPC 缺失会让桌面端停在加载界面。
- Telegram RSA 指纹必须保留 16 位十六进制前导零。
- 裸 `Vector` 返回不能按普通 TL object 序列化，handler 应使用 `bareVector()`。
- TL 可选 string 字段应传 `undefined`，不能传 `null`。
- `ctx.model` 和 `ctx.database` 是独立注入项。
