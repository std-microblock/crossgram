# Device-state memory investigation — 2026-09-20

## Production observations (read-only)

Used the temporary inspect-relay runner; no restart, forced GC, heap snapshot,
load generation, build, or configuration change was made on production. Probes
published counts and aggregate sizes only, not credentials or message contents.

Initial snapshot after ~13.4 days uptime:

- RSS: 869,552,128 bytes (~829 MiB).
- V8 used heap: 161,949,920 bytes (~154 MiB); allocated heap: ~308 MiB.
- External memory: ~31 MiB; ArrayBuffers: ~9 MiB (included in external).
- Nine TCP transports; six hydrated auth-key states, only two with live transports.
- Shared RPC replay: 139 entries / 260,552 body bytes; zero in-flight RPCs.
- Transport send queues, pending updates, and RPC waiters were empty.
- Debug capture was paused with no retained chunks.

The largest **disconnected** state's DialogRpc retained 5,957 users, 5,988 avatar
entries, 5,561 members across 13 group-page caches, 8,919 forward message mappings,
4,490 reverse mappings, and a search cursor. Other disconnected devices retained
additional copies of account data. Counts/serialized lengths are not retained-heap
sizes: maps can share objects, and JS object overhead is not included.

A later runtime snapshot showed ~817 MiB RSS, ~210 MiB used heap, ~320 MiB
allocated/physical V8 heap, and ~31 MiB external memory. Linux reported ~105 MiB
swapped and 208 MiB anonymous huge pages. These are different-time snapshots, not
a before/after optimization comparison. The large RSS/V8 gap remains unattributed;
these probes do **not** establish an allocator leak or explain all process memory.

## Confirmed retention paths

1. Mtproto owns AuthKeyDataStore for the process lifetime. Its map previously
   removed an entry only on explicit auth revocation. Closing the last transport
   did not release the state's DialogRpc caches. Repeated devices/auth keys thus
   accumulated hydrated state even while offline.
2. RpcDependencyRegistry's two-minute reply TTL was only swept during RPC traffic.
   An idle process could retain completed reply bodies indefinitely (bounded by
   the existing 32 MiB/4,096-entry limits). Cache hits also moved entries out of
   completion-time order, so stopping expiry at the first fresh entry could miss
   older expired replies behind it. This was not the main live memory consumer.

## Changes

- Sweep reconstructible auth-key data using the existing five-second service timer.
- Keep every live transport's permanent auth key pinned, including parallel media
  sockets; retain disconnected keys while a shared RPC remains in flight.
- Retain state for a five-minute idle grace period for ordinary reconnects.
- Refresh timestamps on reads, writes, and sweeps observing active keys.
- Evict only the in-process cache and its in-process API-layer lookup; durable
  authentication, account bindings, and persisted API layers remain untouched.
- Rehydrate through the existing resolver on the next cache miss.
- Clear hydrated state and layer lookups on service shutdown.
- Sweep completed replay bodies even without traffic; scan past fresh entries
  because replay-hit order is not expiry order. Track the earliest expiry to skip
  full scans on the ordinary RPC path when capacity limits are satisfied. Never
  evict unfinished replies.

This addresses offline-device accumulation, **not** duplication among simultaneously
active devices. Sharing all DialogRpc instances would be unsafe: they carry the
originating auth key, including draft/update exclusion behavior. A later change
could extract account-scoped read-through caches while keeping per-device actions
separate, with invalidation and concurrent access tests.

## Reproducible local retained-cache benchmark

Run from the repository root on the workstation, not the production server:

~~~sh
node --expose-gc --import tsx scripts/profile-device-memory.ts 8 6000 --no-prune
node --expose-gc --import tsx scripts/profile-device-memory.ts 8 6000
node --expose-gc --import tsx scripts/profile-device-memory.ts 16 6000
~~~

The benchmark uses the real AuthKeyDataStore with synthetic user/avatar/member/
message-map payloads, 6,000 users per device, and one device left active. It does
not model an entire Crossgram process or a live multi-device Telegram workload.
Each run is a fresh Node process; local forced GC measures surviving JS heap above
baseline rather than equating RSS with live objects.

| Policy / devices | Loaded cache heap | Heap after idle sweep + GC | Evicted devices |
| --- | ---: | ---: | ---: |
| Before-policy / 8 | 30.17 MiB | 30.27 MiB | 0 |
| New policy / 8 | 30.18 MiB | 3.97 MiB | 7 |
| New policy / 16 | 60.25 MiB | 4.46 MiB | 15 |

For eight synthetic devices, surviving incremental heap fell ~87%. This is **not**
an 87% reduction in production RSS. RSS did not immediately fall by the amount of
released heap even locally. Active-device caches still scale with active devices.

## Rollout / remaining work

This change has not been deployed by this investigation. After deployment, compare
connected permanent keys versus hydrated states after at least five idle minutes,
and compare heap trends under equivalent traffic. Do not treat immediate RSS as
proof of cache retention. Native/allocator and active-device duplication analysis
are separate follow-ups; do not enable allocator changes on this small production
host without a controlled staging comparison.
